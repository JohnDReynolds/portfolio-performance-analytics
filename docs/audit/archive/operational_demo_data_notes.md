# Operational Demo Data Notes

These notes document how the Axys/APX and performance-comparison demo data was
derived from the packaged Mega-Cap Alpha Portfolio. They are retained as
historical/process notes. The active forward-looking roadmap is
[`roadmap.md`](../../roadmap.md).

## Objective

Create small, believable operational demo files that share the same source
universe as the analytics demo, while staying compact enough for workbook and
Axys/APX-demo review.

The operational demos should eventually include:

- a handful of Mega-Cap Alpha Portfolio equities;
- `CASHUSD` cash-holding rows;
- a few T-bill and T-note style instruments with accrued interest;
- six monthly periods;
- three small portfolios (`ALPHA`, `BALANCED`, and `INCOME`);
- controlled restatements for performance-comparison examples.

## Phase 1: Prototype Generated Source-data

Status: complete.

The first prototype is generated by:

```bash
./.venv/bin/python scripts/operational_demo_data/derive_operational_demo_data.py
```

It writes only under:

```text
_demo_output/operational_demo_data_generation/
```

The generator currently:

- reads `ppar/setup_templates/generic_analytics/performance/Mega-Cap Alpha Portfolio.csv`;
- keeps a small set of high-weight equities over recent monthly periods;
- splits the analytics cash sleeve into `CASHUSD`, `912797AA1`, `91282Y2Y1`,
  and `91282Y5Y1` operational securities;
- creates the ALPHA, BALANCED, and INCOME portfolio variants from the same
  security universe;
- creates Axys/APX-style `portperf`, `secperf`, `secref`, holdings, and
  transactions CSVs;
- writes `summary.json` for quick inspection.

The fixed-income rows are intentionally synthetic. They are designed to produce
clear accrued-interest, price, market-value, and cash examples rather than to
model CUSIP-level Treasury pricing.

## Phase 2: Manual Review

Review the generated files for:

- understandable security list;
- realistic enough cash/fixed-income sleeve;
- period count and date range;
- weights summing to 1.0;
- useful accrual and transaction examples;
- whether the file shapes look compatible with current Axys/APX imports.

## Phase 3: Axys/APX Analytics Demo Replacement

Status: complete.

The Axys/APX analytics fixture is generated by:

```bash
./.venv/bin/python scripts/operational_demo_data/derive_axysapx_analytics_demo_data.py
```

It writes:

```text
ppar/setup_templates/axysapx_analytics/portperf.csv
ppar/setup_templates/axysapx_analytics/secperf.csv
```

The configuration file is:

```text
ppar/setup_templates/axysapx_analytics/axysapx_analytics.yaml
```

The goal is for the Axys/APX analytics demo to tell the same broad story as the
core Mega-Cap analytics demo, while still looking like an Axys/APX-style export.
The test suite verifies that the Axys/APX-shaped security performance is a lossless
wrapper around the canonical Mega-Cap portfolio and benchmark CSV files.

## Phase 4: Performance Comparison Snapshots

Status: complete.

Create snapshot A and snapshot B directories from the generated operational
data. Snapshot B introduces controlled changes that produce:

- mostly fully explained ALPHA, BALANCED, and INCOME portfolio-period
  differences;
- one partly explained ALPHA period with a changed transaction amount plus
  review-only transaction quantity, price, and commission clues;
- one partly explained INCOME fixed-income period with paired 91282Y5Y1
  `by`/`pa` and `sl`/`sa` rows, quantity-driven holding value/accrual evidence,
  and reviewer triage for incomplete or overlapping estimates;
- related holding-component examples where quantity rows sit beside selected
  market-value rows and cost remains in the promoted `source_detail.csv`;
- matching security-level examples for AAPL and 91282Y2Y1;
- transaction-rule YAML plus default field-role treatment for performance
  inputs, input components, reported-performance diagnostics, and context fields.

The current generator writes:

- `axys_a/`: baseline operational Axys/APX-style snapshot;
- `axys_b/`: restated snapshot with controlled changes;
- `axysapx_performance_comparison.yaml`.

The generated YAML files validate and run through `compare_snapshots`. The
portfolio demo intentionally does not use strict causal-attribution mode because
it includes one review-only unexplained period. The accepted snapshot files are
promoted into `ppar/setup_templates/axysapx_performance_comparison/snapshot_a/` and
`ppar/setup_templates/axysapx_performance_comparison/snapshot_b/`, where the user-facing portfolio and
security comparison demos consume them.

After intentional fixture edits, rebuild and audit the scenario-derived holdings
and derived security/portfolio performance files with one command:

```bash
./.venv/bin/python scripts/operational_demo_data/rebuild_performance_comparison_demo_data.py
./.venv/bin/python scripts/operational_demo_data/rebuild_performance_comparison_demo_data.py --write
```

The default command audits without writing. The `--write` command validates
`scripts/operational_demo_data/performance_comparison_transaction_scenarios.csv`
and derives snapshot B `transactions.csv` from snapshot A plus those scenario
rows. It then derives simple transaction-driven holding impacts from changed
`by`, `sl`, `wd`, `dv`, `in`, and fee-like `dp` rows; validates
`scripts/operational_demo_data/performance_comparison_holding_scenarios.csv` for
residual non-transaction holding scenarios; derives snapshot B `holdings.csv`
from snapshot A plus those impacts; then recomputes derived `secperf.csv` and
`portperf.csv` fields and runs the same audit guardrails. The legacy
`scripts/audit_performance_comparison_demo_data.py` command is only a wrapper
around this rebuild/audit implementation.

The residual holding scenario file uses explicit `scenario_type` values so
remaining non-transaction adjustments are named and validated:

- `valuation_mark`
- `cash_balance_correction`
- `quantity_valuation_correction`
- `accrual_correction`
- `cost_only_correction`

The rebuild/audit summary also reports scenario counts grouped by transaction
code and holding scenario type. That makes it possible to confirm the demo still
contains the intended examples without opening the fixture CSV files.

The workbook should answer:

```text
This performance difference happened, and these underlying source-data
differences explain it.
```
